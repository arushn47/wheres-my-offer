Initial features implemented on 7 October 2026. The user subsequently applied v44/v45 on Mumbai and authorized a venue-only historical backfill across all drives. The all-drive backfill is complete; application deployment and database backfill are separate operations.

## Behavior

- Every timeline action uses an authenticated same-site resolver. Personal messages resolve only through their owner's connected account. Shared college circulars resolve in the clicking user's college account; shared-ingester Gmail IDs are never used for another recipient.
- Existing mailbox-local IDs open directly. Otherwise a click performs one exact RFC Message-ID Gmail lookup requesting only message/thread IDs, including archived/spam/trash mail. Missing, ambiguous, disconnected or quota-blocked results offer an explicit exact-search/inbox fallback. No subject guessing, bodies, sync dispatch, mailbox mutations or account-state changes.
- Private mappings are isolated by account/source and encrypted refresh-credential fingerprint. An atomic database claim coalesces clicks and limits lookup starts to 20 per account per minute. Failed/missing results wait five minutes; positive mappings expire after 30 days. Google handles browser account selection and sign-in. Gmail UI links still need a real signed-in browser acceptance check; the REST API does not promise a web permalink contract.
- Drive Mode describes required attendance: **Own location**, the named lab/campus, or a company office. An online test platform does not imply permission to attend from home. A confirmed campus/lab/office takes priority over remote rounds in the headline; **Recruitment: VIT Vellore; Test: Own location** displays **VIT Vellore**, with both rounds retained in the details. When rounds have different destinations, the headline names one required physical destination, prioritizing travel and later rounds; all round venues remain in the details. A plane marks physical attendance away from the known home campus. Bhopal lab attendance displays **Bhopal LC** without a plane. It uses only the exact drive's bounded `recruitment_venues` projection. Unknown locations display **To be announced**. No job-location/status-note/event-default/sibling-drive fallback. Same-campus rooms deduplicate.
- Canonical ingestion stores deterministic venue extraction with existing job-detail parsing, then re-extracts from the already loaded circular when writing venues so older cached parser results cannot restore incorrect locations. Only high-confidence exact assignments can update the venue projection automatically. A company-name-only assignment is excluded. The database additionally requires the exact primary canonical anchor or matching explicit drive numbers; conflicting/pooled numbers and admin-excluded sources are rejected. Atomic row locking preserves newer same-stage instructions; venue updates do not modify activity timestamps or recruitment state.
- All pages use the same display resolver. Reads request only compact venue metadata in batches of 200; no new page-body reads, polling or Gmail calls while rendering. Existing admin-excluded source IDs are filtered out.

### Sync diagnosis and correction

Live read-only checks confirmed the personal Gmail watch is active and pushes are arriving. The Hitachi confirmation received at 23:46 IST on 8 October was stored and processed; its application now reads `applied`. The observed delay had several code causes:

- Personal discovery always searched the entire placement season, even with a valid history cursor. Saved messages were deduplicated, but discarded/noise messages could be repeatedly rediscovered. Normal sync now consumes added-message history only. A full season search is reserved for initial discovery or an expired cursor.
- A personal push ran one budget-limited sync and acknowledged completion despite pending pages. It now drains durable pages under one bounded invocation deadline, verifies the account cursor covers the notification, and returns a retryable response for locks, failures or unfinished work. Completed push redeliveries do not acquire another inbox claim.
- Small batches were ephemeral. Every new batch, including one email, is now persisted before its discovery cursor advances. Resumed queue completion never substitutes a later profile cursor. Queue database failures fail closed instead of being mistaken for empty/completed work. Deleted-message 404 responses are terminal skips; quota/auth/network failures remain retryable.
- Watch renewal and reconnect advanced `last_history_id` without processing the intervening mail. They now update watch expiry only.
- The database has no public Realtime publication membership. A visible idle browser now checks an authenticated, user-scoped compact application version every ten seconds, refreshes on change, and restores active progress. This check never starts a Gmail sync or reads message bodies. It stops doing work in hidden tabs and while an active sync/SSE stream is observed. Existing per-user concurrency leases, persisted progress and the daily safety-net cron remain enforced.
- The active shared-college ingester was not writing venue projections. It now merges attendance evidence once per ingested circular, using the original exact anchor/number before registration linking can change that anchor. Existing user fan-out seeds only missing projections from already loaded bodies, covering a drive created after its college circular arrived. Company-only matches, pooled/conflicting numbers, irrelevant sources and contradictory companies cannot write attendance venues; the database rechecks source exclusions and ordering atomically.
