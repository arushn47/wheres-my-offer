# Phase D implementation plan: canonical email content and cross-user deduplication

**Scope:** finish canonical email processing and content deduplication before implementing admin email flagging, assignment overrides, deletion, or reprocess controls. Do not build those admin controls in Phase D.

**Instructions to implementer:** follow these steps in order. Inspect current code at each listed location before editing. Preserve per-user drive assignment, candidate match, status, and RLS behavior. Do not delete existing rows or message bodies until the migration and backfill verification gates pass.

## 1. Current verified state

- `supabase/migrations/migration_v20_canonical_emails.sql` creates `canonical_emails`, `canonical_attachments`, and nullable `emails.canonical_email_id`.
- `src/lib/sync/engine.ts` has `computeContentKey()` and `shadowWriteCanonical()`. `processSingleMessage()` runs normal full fetch, classification, company/drive assignment, status processing, and per-user email insertion first; it then writes/links the canonical row. This is **shadow mode**, not cache-first Phase D.
- No sync path reads `canonical_emails` before requesting full email content or before running the extractors/status engine.
- `canonical_attachments` has schema only; no runtime writer or reader was found.
- Read-only live counts: `emails=8,813` (6,720 college + 2,093 personal); `canonical_emails=1,225`; `6,081` college receipt rows have canonical links; `639` college rows have no canonical link; `canonical_attachments=0`. There are 1,224 referenced canonical rows; one canonical row is currently orphaned. Most referenced canonical bodies have five user receipts, consistent with the same circular delivered to multiple students.
- The DB includes eight users and 15 Gmail accounts. Personal NeoPAT mail is user-specific and MUST NOT be globally merged as if its registration/eligibility content were shared.

## 2. Non-negotiable data model decision

Store **one canonical content/body/parser record** per verified shared message, with **one lightweight receipt/reference row per user/account/message delivery**. Keep `emails` as the per-user receipt table initially, with its existing row ID referenced by `email_drive_links`, `candidate_matches`, `events`, documents, and status history. Link each receipt to one shared `canonical_emails` row.

This achieves “keep the email content once across users” while preserving which user/account received it, each user's drive assignment, and tenant ownership. Do **not** promise that total relational row count will become one row per broadcast: per-user receipt references are required. If the product requirement literally means deleting every per-user receipt except one, stop and request an explicit product/schema decision first; that conflicts with existing user-specific associations and RLS.

After successful rollout, clear duplicated `emails.body_snippet` for linked college receipts (not personal emails), while keeping the canonical body once. This reduces duplicated payload storage without breaking receipt identity. Update every reader that needs the body to join `canonical_emails.body_snippet` through `emails.canonical_email_id`.

## 3. Canonical identity rules

1. Canonicalize only messages from the approved **college broadcast sender(s)**. Do not canonicalize personal `noreply.cdcinfo` messages, user-authored messages, or unrelated sender traffic.
2. Prefer normalized RFC `Message-ID` as a fast cross-mailbox identity when it is present. Request it from Gmail metadata in `src/lib/gmail/client.ts`; normalize whitespace/angle brackets/case for comparison. A Message-ID collision with materially different sender/subject/body is a conflict: do not reuse the canonical row; fall back to full-body content identity and log the conflict.
3. Always compute a content identity from full content before creating/reusing a canonical row when RFC Message-ID is missing or unverified. Use SHA-256 over normalized sender + normalized subject + **full normalized current-message body**, not the current first-500-character prefix. Normalize Unicode to NFC, line endings, HTML-to-text, and repeated whitespace. Preserve words, numbers, attachment references, list entries, and dates. Do not remove arbitrary first-500 prefixes, quoted content, or signatures in a way that can merge materially different shortlist lists.
4. If the canonical identity is uncertain, treat it as a cache miss; fetch and process the user’s email normally. False merge is worse than missed deduplication.
5. Normalize `Re:`/`Fwd:` subject prefixes only for canonical identity, not for the display subject. Store display metadata from a receipt; do not rewrite the user's email timeline subject.
6. Include an identity/parser version in the canonical record or key namespace. A key algorithm change must not silently collide with keys generated by the old first-500 algorithm.

## 4. Schema/migration work

### 4.1 Additive migration

Create the next numbered migration after V22 (inspect the current migration sequence before naming it). It must:

- Add nullable canonical RFC `message_id` (or equivalent) and a partial unique index for non-null values, scoped to approved sender if required by the chosen schema.
- Add indexes needed for lookup by canonical key and canonical RFC Message-ID; keep uniqueness on canonical content identity.
- Add any receipt-level canonicalization state/diagnostic columns only if needed (e.g. `canonicalization_state`, `canonicalization_error`); define allowed values and defaults.
- Keep `emails.canonical_email_id` nullable for personal, unprocessed, and exceptional rows.
- Add no cross-user fields to a per-user row that expose another user's receipt or Gmail metadata.
- Preserve RLS. `canonical_emails` contains shared public-to-eligible-users college circular content and must not become directly readable by unauthenticated users. Add authenticated read policy only after checking the project's authorization model; all service-role writes remain server-side.
- Do not drop or alter `emails.body_snippet` in the initial migration.

Update `supabase/schema.sql` and `supabase/schema-simple.sql` to represent the resulting deployed schema. Do not overwrite unrelated existing dirty edits.

### 4.2 Backfill existing rows in batches

Add a resumable server-side/scripted backfill that:

1. Selects eligible college receipts whose `canonical_email_id IS NULL`, in stable bounded batches.
2. Re-fetches full Gmail content only when needed to calculate the new full-body key. Respect account ownership and reconnect/error handling; never use one user's Gmail credentials for another user's message.
3. Upserts the canonical content safely on key conflict, then updates that user's receipt's `canonical_email_id`.
4. Does not change `placement_drive_id`, assignment state/source, classification, application status, candidate matches, event rows, manual overrides, or timestamps used for status recency.
5. Is idempotent: rerunning it creates no duplicate canonical rows and does not overwrite a correct canonical body with incomplete/truncated content.
6. Records progress, retries transient Gmail/database failures, supports dry-run/count mode, and can resume after timeout.
7. Reports: processed, linked, skipped (personal/unapproved), failed, key conflicts, canonical rows created/reused, and orphan canonical rows.

## 5. Cache-first sync (Phase D core)

### 5.1 Change Gmail metadata fetch

In `src/lib/gmail/client.ts`, extend `MessageMetadata` and `fetchMessageMetadata()` to include RFC `Message-ID` when available. Keep the existing sender, subject, date, and snippet behavior.

### 5.2 Add canonical lookup before full fetch

In `src/lib/sync/engine.ts`, integrate in the existing `processPage()` prefetch sequence, after trusted-sender filtering and metadata fetch, before `fetchMessageDetail()`:

1. Look up an already verified canonical row by RFC Message-ID for an approved college sender.
2. If absent, only use a cheap metadata/snippet key as a **candidate lookup**, never as conclusive identity unless uniqueness and collision-safety are proved. For uncertain/no match, fetch full body and verify by full content key.
3. On verified hit, do not download/parse the same shared body or attachments again. Build a per-user `ParsedEmail`/receipt input from canonical subject/body/parsed fields plus this mailbox's metadata (`gmail_message_id`, `thread_id`, `received_at`, labels, attachment IDs/account).
4. Still create/update that user's `emails` receipt and set `canonical_email_id`.
5. Still run per-user drive resolution, `email_drive_links`, status processing, candidate match association, notifications, and assignment rules using the reconstructed email. Reuse shared **parsing**, never shared user-specific status/match/drive decisions.
6. On cache miss, full-fetch and parse normally; upsert canonical parsed content; create/link receipt; continue user-specific processing.
7. On canonical store or lookup failure, fall back to today's full processing without dropping the email. Canonical cache failure must never cause status processing to be skipped.
8. Do not let one receipt's `placement_drive_id`, user ID, Neo ID, candidate match, status, or attachments authorization leak into another user. A canonical row must contain only content-level parse output.

### 5.3 Processing ownership and concurrency

Use a canonical processing claim/lease for a new shared content key if parsing/attachment work can overlap across users. Reuse the existing sync lease rules where applicable; do not create unlocked global work that can overlap cron. If no safe claim is available, perform idempotent upserts and allow duplicate computation, but never duplicate canonical rows or associate partial parse output as complete.

## 6. Move parsing outputs and attachments to canonical scope

- Populate `parsed_company_name`, `parsed_drive_numbers`, `parsed_job_details`, and `parsed_events` for new canonical records only from deterministic, shareable extraction. These fields are cache data; live drive/status assignment remains per user.
- Implement `canonical_attachments` only as a later substep after message canonicalization works. Deduplicate file bytes by content hash; associate candidate matches/attachment references with each user's receipt/drive separately. Never use one user's Neo ID result as a global result.
- Do not mark canonical content complete if attachment parsing is pending/failed unless the completion semantics explicitly separate body parsing from attachment parsing.

## 7. Update all body readers before removing duplicate bodies

Search the whole repository for `.from('emails')`, `body_snippet`, and `emails.*` joins. Update any reader that needs message content to retrieve canonical body text, including at least:

- `src/app/api/sync/reprocess/route.ts` (all-email reads and status recalculation)
- `src/app/(dashboard)/companies/[id]/page.tsx` (Circular & Email Timeline)
- `src/app/(dashboard)/search/page.tsx`
- any reprocess, orphan relink, attachment scanner, or admin/diagnostic route that reads email body text.

Keep sender, mailbox type, received time, user receipt ID, assignment fields, and display subject from the receipt. Render body content from the canonical row when linked; fall back to legacy `emails.body_snippet` when no canonical row exists.

Only after every body reader is updated and verified, add a **separate** cleanup migration/job that nulls `emails.body_snippet` for successfully linked eligible college receipts. Do not delete per-user receipt rows or personal-email bodies in this phase.

## 8. Tests required before rollout

Add meaningful tests for:

1. Same approved college message delivered to five users → one canonical content row, five user receipts, all linked, each with independent user/account/drive assignments.
2. Same subject and same first 500 chars but different text later (e.g. different shortlist candidate lists) → distinct canonical keys; no false merge.
3. Same RFC Message-ID and same normalized content across users → canonical hit avoids full-body Gmail fetch on the second user while still creating their receipt and running their own status/drive logic.
4. Same RFC Message-ID but differing body → conflict/fallback full fetch, never reuse the mismatched canonical body.
5. Missing RFC Message-ID → full content hash path, exact identical broadcast reuses canonical row; changed content does not.
6. Personal NeoPAT message received by multiple users → never globally canonicalized; user-specific content remains isolated.
7. Canonical lookup/insert outage → normal sync fallback still creates receipt and processes status once.
8. Backfill rerun → idempotent; no changes to drive assignments/status recency/manual overrides.
9. Timeline/search/reprocess continue showing the same text before and after linked college `body_snippet` is cleared.
10. Cross-tenant/RLS checks: one authenticated user cannot enumerate another user's receipts or private Gmail metadata through canonical joins.

## 9. Rollout gates and operations

1. Deploy migration first; verify live schema and indexes.
2. Deploy code in **shadow/read-compare mode**: compute canonical identities and log/cache-hit eligibility, but do not skip full fetch yet. Compare identities, collisions, parser output, and counts for representative batches.
3. Run resumable backfill with dry-run first. Confirm canonical rows are deduplicated and every linked receipt points to the expected body; resolve all conflicts.
4. Enable cache-first behavior behind a server-side feature flag for a small cohort, then expand after logs show correct user-specific assignments and no cross-tenant leakage.
5. Compare Gmail full-fetch counts, canonical hit counts, parser invocations, per-user receipt count, status transitions, errors, and sync duration before/after.
6. Only after all body consumers support canonical fallback, clear duplicate college receipt bodies in a separate resumable cleanup.
7. Rollback: disable cache-first flag and return to full fetch + current shadow-write path. Keep canonical tables/links; do not delete canonical or receipt records as rollback.
8. Preserve current per-user `emails` receipts and their IDs throughout Phase D. Do not combine this rollout with the later email-ignore/admin assignment project.

## 10. Completion criteria

Phase D is complete only when all are true:

- Identical approved college broadcast content is stored once in `canonical_emails` across users.
- Each recipient still has a lightweight per-user receipt row and independent drive/status associations.
- A verified canonical hit avoids repeat full-body fetch/parse work when RFC identity permits; uncertain identity safely falls back to full fetch.
- Personal NeoPAT emails are not shared/canonicalized.
- No per-user status, Neo ID match, drive assignment, or private mailbox field is stored/reused globally.
- All email body readers work with canonical-linked receipts; college receipt bodies can be cleared without UI/reprocess regressions.
- Backfill is idempotent, resumable, counted, and safe around cron overlap.
- Required tests and rollout gates pass.

## Explicitly deferred

Do not implement Deloitte/Honeywell email ignore flags, admin review UI, email deletion, manual drive assignment, or reprocess-all-users tools until Phase D is complete. Those will operate on preserved per-user receipt IDs and should use a separate persistent override/decision model.
